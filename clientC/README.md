# APP1 - AppoLab project

This repository contains the different clients I made for the AppoLab exercises during APP1.

Most of the project is written in C since this is what we used for the course. There is also a Rust version of the `OneMillion` challenge because I usually code in Rust and wanted to see if I could get better performances with it.

The clients connect to:

```text
im2ag-appolab.u-ga.fr
```

They then send commands to AppoLab, read the answers and depending on the exercise either decode something, modify the response or compute an answer before sending it back.

## Compiling the project

For the C clients, just run:

```sh
make
```

The executables are put inside the `bin/` directory.

For example:

```sh
./bin/client-interactif
./bin/client-tutoriel
./bin/client-NorthWoods
```

If you modify one of the C files, don't forget to run `make` again before testing it.

To remove the build files:

```sh
make clean
```

And to also remove the executables:

```sh
make clear
```

## Login / `.env`

Most of my automated clients read the AppoLab login command from a `.env` file at the root of the project.

It should contain something like:

```text
login <login> "<password>"
```

The programs are normally meant to be launched from the root directory because they also access files such as `.env` and the `commands*.txt` files using relative paths.

Obviously the real `.env` should not be committed since it contains the password.

## Project structure

The project is mostly organised like this:

```text
.
├── Makefile
├── commands*.txt
├── src/
│   ├── client.c
│   ├── client.h
│   ├── client-interactif.c
│   ├── client-tutoriel.c
│   ├── client-OneMillion.c
│   └── other client-*.c files
├── bin/
├── build/
└── rust-OneMillion/
```

`src/client.c` and `src/client.h` contain the common networking code used to communicate with AppoLab.

Then most exercises have their own `client-<exercise>.c`.

The `commands*.txt` files are simply lists of commands that some clients send to AppoLab automatically instead of having to type everything each time.

`bin/` contains the compiled programs and `build/` contains the object files generated by the Makefile.

## The different clients

### `client-interactif`

This is basically the starting client.

It lets you communicate with AppoLab manually by typing commands in the terminal. It was useful at the beginning to understand how the server works, and also later to test an exercise before automating it.

Run it with:

```sh
./bin/client-interactif
```

### `client-tutoriel`

This is the first automated version.

Instead of entering the tutorial commands manually, it reads them from `commands.txt` and sends them to the server.

There is also `client-tuto-fort` for the other tutorial exercise.

### `client-BayOfPigs`

This one uses the `crypteMove` functions.

The server sends encrypted data, so the client has to decode it and sometimes encode another message before sending the answer.

The related functions are in:

```text
src/client-crypteMove.c
src/client-crypteMove.h
```

### `client-NorthWoods` and `client-LostCause`

These use the functions from `client-cryptseq.c`.

There are a few different transformations in there such as `cryptseq` and `cryptassoc`.

I put the common code in a separate file instead of rewriting the same functions in every client.

### `client-projetX` and `client-planB`

These use frequency analysis to try to recover the shift of a Caesar-like cipher.

The common part is in:

```text
src/client-projetX.c
src/client-projetX.h
```

`client-planB` reuses that implementation instead of having another copy of it.

## OneMillion

`OneMillion` is the exercise on which I spent the most time trying to optimize things.

The goal is basically to work with a string which would eventually contain one million characters, while the timed part of the exercise needs to be extremely fast.

A naive version which actually moves the complete string every time would be way too slow, so I used a circular/ring buffer instead.

The important idea is that rotating a string doesn't actually require moving every character. You can keep the data where it is and only change where you consider the beginning of the buffer to be.

### Precomputing as much as possible

The server gives us a known base before the actual timed part.

Because of that I precompute everything I can before sending `start`.

The result of this preprocessing is basically a small plan telling the program where each of the first 100 final characters will come from.

Then when `start` gives the last 100-character key, there is only a very small amount of work left to do.

This is what `prepare_prefix()` and `apply_prefix()` in:

```text
src/client-OneMillion.c
```

are doing.

I also added a few network optimizations in:

```text
src/onemillion-net.c
```

because at this point the computation itself became so fast that network latency was a pretty big part of the final time.

The C version is compiled with `-O3` separately from the other clients:

```sh
make onemillion
```

Then:

```sh
./bin/client-OneMillion
```

It also accepts a number of attempts from 1 to 20:

```sh
./bin/client-OneMillion 5
```

I mainly added this because the network timing can vary quite a bit between attempts.

## Rust OneMillion version

There is also another implementation in:

```text
rust-OneMillion/
```

I made this one mostly because Rust is the language I am more used to, so I wanted to try writing the complete client myself instead of reusing the C networking implementation.

It uses more or less the same main idea as the C version, but the networking part is also rewritten in Rust.

To compile it:

```sh
cd rust-OneMillion
cargo build --release
cd ..
```

Then from the project root:

```sh
./rust-OneMillion/target/release/client-onemillion
```

There are also a few options I added while testing it.

Run multiple attempts:

```sh
./rust-OneMillion/target/release/client-onemillion 5
```

Wait until the connection latency seems low before starting:

```sh
./rust-OneMillion/target/release/client-onemillion --wait-low-latency
```

And run only the local computation benchmark:

```sh
./rust-OneMillion/target/release/client-onemillion --benchmark
```

The Rust version ended up being slightly better for me. Part of that is probably because I understand Rust much better than C, and I also rewrote the complete client so I had more control over what happened during the timed section.

For example, the Rust version can prepare some things while the network thread is doing its work and then join it when the result is needed.

## If something doesn't work

If a program says it cannot open a file, first check that you are running it from the root of the repository.

For example this is correct:

```sh
./bin/client-NorthWoods
```

while being inside another directory can cause `.env` or one of the command files not to be found.

If you changed some C code and it looks like nothing changed, rebuild it:

```sh
make
```

or rebuild everything:

```sh
make clear
make
```

The programs obviously also need access to the AppoLab server, so a connection error isn't necessarily caused by the client itself.
